# 马甲系统规范（SPEC）

版本：2.0
状态：草案

---

## 1. 系统定位

### 1.1 核心定位

**马甲系统 = 非技术层面的伪专家召唤系统**

类似于 WorkBuddy 中召唤专家：
- 专家回答特定场景的专业知识问题（技术层面）
- 马甲系统解决非技术层面的专业需求（认知翻译）

**本质**：用户生活语言 ↔ AI专业执行语言的认知中间件

### 1.2 与专家系统的区别

- 维度一：WorkBuddy专家处理技术知识，马甲系统处理认知翻译
- 维度二：WorkBuddy专家输出知识回答，马甲系统输出可行性结果/建议/方案
- 维度三：WorkBuddy专家触发固定领域，马甲系统按需动态触发
- 维度四：WorkBuddy专家覆盖专业问答，马甲系统覆盖无限制领域

### 1.3 核心原则

1. **Token 大幅减少**：代码层意图执行，RAG 检索主导
2. **零预设领域**：不预设任何具体领域，按需动态生成
3. **规则模块化**：公共规则统一管理，领域规则按需加载

## 2. 核心概念

### 2.1 马甲系统是什么

不是单纯的提示词生成器，而是：

**认知中间件**：弥合用户意图与表达之间的鸿沟

```
用户脑中有一个画面
    ↓
但缺乏专业词汇精确表达
    ↓
马甲系统帮你翻译
    ↓
AI 能精准执行
```

### 2.2 输出范围

马甲系统不只生成提示词，输出范围包括：

**生成类**：文生图/视频/音频的提示词

**可行性建议**：心理咨询、职业规划、决策分析

**多维度分析**：市场分析、竞品对比、风险评估

**流程规划**：项目计划、学习路径、职业规划

**直接回答**：知识查询、概念解释、方案推荐

## 3. 运作逻辑

### 3.1 完整流程

```
用户输入
    ↓
【第一步】安全红线检查
    ↓
【第二步】意图识别
    ↓
【第三步】规则加载
    ↓
【第四步】处理执行
    ↓
【第五步】输出结果
```

### 3.2 Token 消耗分析

**SKILL版（纯文本规则）**：

```
用户输入 → 模型解析意图 → 模型加载规则 → 模型生成答案 → 模型输出
```

全程靠模型处理，每一步都消耗 Token。这是 SKILL 版本的固有局限。

**代码版（Python / Java）**：

```
用户输入 → 代码安全预检 → 代码分类意图 → 代码RAG检索 → 代码组装最小上下文 → 模型生成 → 输出
```

前四步全在代码层完成，不消耗 Token。模型只在最后一步介入，且接收的是已压缩过的最小上下文。

### 3.3 代码层执行内容（仅代码版有效）

代码负责（不消耗Token）：
- 安全红线关键词预检
- 意图分类（从 domains/*.yaml 动态读取关键词匹配）
- RAG检索（本地文件检索，只取最相关 top_k 条）
- 上下文压缩（只把必要的术语和追问传给模型）

模型只负责（消耗Token）：
- 理解压缩后的上下文
- 生成最终答案

### 3.4 版本功能差异

版本选择建议：
- 优先推荐：下载完整ZIP
  原因：
    - 自动RAG检索（静默后台运行）
    - 一键缓存（用户偏好自动保存）
    - 完整效果（快车道/完整流程自动判断）

- 备选方案：添加SKILL方式
  前提：用户愿意手动配合
  效果：≈70%完整功能
  限制：
    - 无法自动RAG检索（需用户手动触发）
    - 无法一键缓存（无持久化存储）
    - 无法判断快车道（每次都是完整流程）

SKILL版不支持：
  - 缓存决策与流程选择 ← 平台无法读取本地缓存
  - 自动RAG检索 ← 依赖 scripts/ 脚本
  - 用户偏好记忆 ← 无持久化存储
  - 快车道热启动 ← 无缓存状态

代码版专属：
  - 上述全部功能
  - 代码层意图执行（Token大幅减少）

SKILL版本的兜底机制：
  说明：即使没有缓存，SKILL版本仍有兜底能力
  缓存解决什么问题：
    - 已知偏好时的效率问题（快车道）
    - 减少重复描述（记住用户风格）
  调研解决什么问题：
    - 未知需求时的澄清问题（M1模式）
    - 需求模糊时的意图挖掘
  两者关系：
    - 缓存与调研是互补的，不是替代关系
    - 没有缓存时，M1调研探索仍能完成目标
  实际效果：
    - 无缓存无检索：≈30%效果（仅靠通用规则硬扛）
    - 无缓存+主动检索：≈70%效果（需用户配合）
    - 无缓存+M1调研兜底：≈60%效果（适合需求模糊场景）

## 4. 规则架构

### 4.1 规则目录结构

```
rules/
├── 通用红线.md     ← 所有领域共享的安全约束
├── 输出规范.md     ← 格式禁令、输出结构
└── 运作逻辑.md     ← 意图识别、流程控制
```

### 4.2 规则加载策略

- **通用规则**：始终加载
- **领域规则**：按需加载
- **平台规则**：指定平台时加载

### 4.3 领域规则生成

首次遇到新领域时：

1. 基于通用框架 + 用户描述动态生成
2. 展示给用户确认
3. 确认后保存到 storage/领域库/

## 7. API 配置

Java/Python 版本支持用户使用自己的模型 API。

### 7.1 Python 配置

文件：config.yaml

```yaml
api:
  provider: "openai"
  base_url: "https://api.openai.com/v1"
  api_key: "${API_KEY}"
  model: "gpt-4"
```

### 7.2 Java 配置

文件：application.yaml

```yaml
majia:
  api:
    provider: "openai"
    base-url: "https://api.openai.com/v1"
    api-key: ${API_KEY}
    model: "gpt-4"
```

### 7.3 支持的 Provider

支持的模型提供商包括：
- openai
- claude
- deepseek
- zhipu
- moonshot
- 自定义（需提供 base_url）
